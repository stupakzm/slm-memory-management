Knowledge Trees for Small Models

What the published work says about building a local, structured knowledge store that a 1.5–4B model can actually use on cheap hardware — and, critically, which part of that job the small model must not be given.

The finding that reshapes the design

The intuitive architecture — point a local 3B model at your Linux books and let it build a knowledge tree — is the single best-documented failure mode in this literature. Not a quality problem. A crash.

The fix is not a bigger model. It is a split of roles: whatever builds the structure is a separate concern from whatever answers the question, and only the second one needs to be small, local, and fast. Everything below follows from that split.

Five findings that constrain the build

Finding 01 · Load-bearing

Small models cannot build the graph. The floor is ~7B, and it fails hard, not gracefully.

LLM-driven knowledge-graph construction (GraphRAG and descendants) asks the model to emit strict JSON entity/relation records for every chunk. Sub-7B models do not reliably produce parseable JSON at that volume, and the pipeline dies rather than degrading.

Evidence
Microsoft GraphRAG v2.3.0 on a GTX 1070 Ti (8 GB): Phi-4-mini (3.8B) crashed with FailedToGenerateValidJsonError after extracting just 16 entities and 5 relationships. The authors set "a practical minimum model size of approximately 7B parameters for reliable GraphRAG operation."
FastGraphRAG is reported incompatible with 7–8B models entirely — the required structured output could not be obtained even with five retries per call.
Even when it works it is slow: indexing one documentation set took 88 min (Qwen 2.5 7B) to 211 min (Llama 3.1 8B); global search queries ran 110–281 s.
Your 1.5–4B model is the reader, never the indexer. Build structure by other means (Finding 03), or run a one-time offline build with a larger model.
Finding 02 · Load-bearing

Small models are actively harmed by irrelevant retrieved context.

Retrieval utilisation does not scale uniformly with parameter count. Models under 4B are measurably poor at discriminating useful passages from noise in their context window, and degrade when fed contradictory ones — the opposite of the large-model habit of tolerating a generous top-20 dump.

Evidence
Sub-4B models show "poor robustness to noisy or contradictory retrieved passages, frequently generating incorrect or confused responses." The recommendation is aggressive retrieval filtering — only high-confidence passages.
Anthropic's contextual-retrieval benchmarks quantify the upside of getting this right: retrieval failure 5.7% → 3.7% with contextual embeddings → 2.9% adding BM25 → 1.9% adding a reranker.
Precision beats recall here, and by more than usual. Budget for a reranker from day one and pass 3–5 chunks, not 20. A reranker is not a late optimisation on this stack — it is what makes a 4B model usable.
Finding 03 · Enabling

Structure can be built with no LLM at all — 100–1000× cheaper, and often more accurate.

A 2026 line of work removes the LLM from index construction entirely, deriving hierarchy and graph topology from embedding geometry, clustering, and co-occurrence statistics. These are not merely cheaper; several beat the LLM-built graphs on retrieval quality.

Evidence
LiteSemRAG builds a heterogeneous semantic graph from contextual token embeddings with zero LLM tokens. MRR@10 of 0.694 on HotpotQA vs LightRAG's 0.419; ~20× faster indexing than LightRAG, ~10× than GraphRAG.
ContextRAG builds a 3-level hierarchy by residual-quantised k-means over chunk embeddings: 22,073 indexing tokens vs 23,017,780 (1043× lower), 30 LLM calls vs 5,655, 563 s vs 237,938 s. The topology costs zero tokens; the small token spend is only cluster summaries.
RAPTOR remains the reference "actual tree": recursive clustering plus abstractive summarisation, leaves to root, retrievable at any level of abstraction. The LLM is needed only to summarise clusters — batchable, one-time, and safely delegated to a bigger model.
Your knowledge tree is buildable without a capable LLM in the loop. And for the Linux corpus specifically, most of the hierarchy already exists — man page sections, wiki headings, book chapters are the tree. Parse it; don't infer it.
Finding 04 · Directly addresses your requirement

"I don't know" has to be architectural. Prompting for it does not work at this scale.

You named this as a hard requirement, and it is the one most often implemented wrongly — as a line in the system prompt. A 3B model asked to self-assess its own certainty is unreliable. The robust designs never reach the model at all when evidence is thin.

Evidence
Retrieval confidence works as "an interpretable proxy for evidence sufficiency" — abstain before generation when top scores fall below threshold, so no speculative synthesis can occur.
HALT-RAG uses calibrated NLI ensembles to check the generated answer against retrieved context, with an explicit coverage target (e.g. 90%) and an uncertainty band that gets rejected — trading a little coverage for a large precision gain.
The threshold is not guessable. The standard method is a labelled set, swept across threshold values, choosing the precision/recall point your domain needs.
Three independent layers: (1) a score gate before generation — if nothing clears the reranker threshold, return a fixed "I don't have that" and never invoke the model; (2) grammar-enforced citation of chunk IDs, so an uncited claim is structurally impossible; (3) an optional NLI check on the output. Layer 1 alone buys most of the benefit.
Finding 05 · Enables your tool-use goal

Tool use at 1.5–4B is viable — but only with constrained decoding and a tiny tool set.

Free-form function calling at this scale is mediocre. Grammar-constrained decoding plus validate-before-execute changes the picture completely, which is convenient, because llama.cpp ships exactly that in GBNF.

Evidence
Unconstrained on BFCL: xLAM-2-3b-fc-r 65.74%, Qwen3-4B 62.04%, Qwen3-1.7B 55.49%. Models under 1B fail multi-turn, parallel and multi-function tasks outright.
With schema enforcement and validator-first execution, Phi-4-mini reaches ≥97% function-call accuracy on BFCL-v4 — matching or exceeding 70B models. Constrained JSON decoding costs 5–60% latency depending on backend and schema.
Fragility is real: surface paraphrasing of the user's query causes 11–19% absolute AST accuracy drops, and adding semantically-related distractor tools costs another 1–8%.
Keep the tool set small and scoped per domain rather than exposing one global toolbox. For a system-tweak assistant, make the default output an explained command the user confirms — execution behind an explicit gate, not the default path.

Recommended architecture

Everything here fits comfortably in 8 GB and runs on CPU if it has to: bge-m3 (568M) + bge-reranker-v2-m3 (568M) + Qwen3-4B at Q4 (~2.5 GB). The published CUBO work demonstrates this class of pipeline inside a 16 GB laptop with a 10 GB corpus, using an embedding-300m model and Llama 3.2 with hybrid dense/sparse retrieval, reranking, and an abstention mechanism.

STAGE 1
Structure-aware ingest
Parse existing hierarchy: man sections, wiki headings, chapters. Free tree.
STAGE 2
Hybrid index
bge-m3 dense + BM25 sparse → sqlite-vec, single file, no server.
STAGE 3
Rerank
bge-reranker-v2-m3 over top-50 → keep 3–5. Non-optional.
STAGE 4
Abstention gate
Below threshold → "I don't know." Model never runs.
STAGE 5
Generate + cite
Qwen3-4B via llama-server, GBNF grammar enforces chunk citations.

Note what is absent: no LLM-built knowledge graph. The hierarchy in stage 1 is parsed, not inferred, which sidesteps Finding 01 entirely. If measurement later shows you need semantic links across documents, add them by LiteSemRAG's embedding-clustering route or a one-time RAPTOR pass with a borrowed larger model — not by asking your 4B to do it at query time.

Implementation and testing plan

These are numbered because the order is the point. Each phase has an exit gate; a phase that fails its gate gets reverted rather than carried forward. The discipline that matters most is phase 0 — most graph-RAG projects never establish whether their structure beat a tuned flat baseline, because they built the structure first.

PHASE 0

Evaluation set, before any system exists

  • 50–100 real questions against your Linux corpus, with the correct source passage recorded for each.
  • 20–30% must be unanswerable — questions the corpus genuinely does not cover. This set measures your core requirement, and nothing else will.
  • Include paraphrase pairs: the same question worded two ways, given the 11–19% paraphrase fragility in Finding 05.
  • Metrics: retrieval recall@k, context precision, faithfulness, and separately abstention precision/recall. ragas runs locally against your own models.
Gate: the eval set exists and is version-controlled before phase 1 begins.
PHASE 1

Deliberately boring baseline

  • Fixed-size chunking, bge-m3 dense only, sqlite-vec, top-5, Qwen3-4B via llama-server.
  • No tree, no graph, no reranker. This number is the thing every later phase must beat.
  • Run the Khoj / RAGFlow comparison here too — if an off-the-shelf tool beats your baseline, that is a genuinely useful result.
Gate: baseline numbers recorded for all four metrics.
PHASE 2

Precision layer — the highest-value work

  • Add BM25 and fuse with dense (BM25 catches --exclude-from, error codes, exact flag names where embeddings fail).
  • Add bge-reranker-v2-m3; cut what reaches the model to 3–5 chunks.
  • Add the abstention gate; sweep the threshold across your labelled set and pick the operating point.
  • Add GBNF-enforced citation of chunk IDs in the output.
Gate: abstention recall high on the unanswerable set without collapsing answer coverage on the answerable set. Expect the largest single jump in the project here.
PHASE 3

Hierarchy — only if phase 2 leaves a gap

  • Structure-derived tree first: document → section → chunk, from headings you already parsed. Retrieve at section level, expand to chunks.
  • Only if that is insufficient, add RAPTOR-style cluster summaries — offline, batched, using a larger model once.
  • Measure against phase 2. Hierarchical summarisation has real costs: information loss and ingestion expense.
Gate: keep it only if it beats phase 2 on the eval set. Revert without sentiment if it does not.
PHASE 4

Tool use, gated

  • GBNF grammar per tool schema; validate arguments before execution, never after.
  • Small, domain-scoped tool sets — expose the 3–5 tools relevant to the current topic, not a global registry.
  • Default output is an explained command awaiting confirmation. Direct execution is opt-in per tool.
  • Add tool-call accuracy and a "refused to act on thin evidence" case to the eval set.
Gate: zero unconfirmed destructive executions across the full eval run.
PHASE 5

User-fed knowledge loop

  • Ingest path for arbitrary user material: paste, file, URL — reusing the phase 1–2 pipeline.
  • Namespace by domain so "Linux" and "cooking" do not dilute each other's retrieval — vector search degrades measurably when unrelated domains share an index.
  • A-MEM-style linking between user notes belongs here, if anywhere.
Gate: adding a second unrelated domain does not regress the Linux eval numbers.

Open decisions

  • Adopt or build. If Khoj plus your corpus already answers your Linux questions well, the project becomes "add a proper abstention gate to Khoj" rather than a ground-up build. Worth one week to find out.
  • Where the one-time bigger model comes from. Phases 3 and 4 benefit from a 7B+ model for offline summarisation. Options: run 7B slowly once on your own hardware, or accept a one-time cloud pass for indexing while all query-time work stays local.
  • Language scope. bge-m3 is the multilingual choice; Qwen3-Embedding-0.6B scores higher on English-only. If your corpus is English-only, that swap is worth testing in phase 1.
